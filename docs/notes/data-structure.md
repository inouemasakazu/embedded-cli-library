# データ構成 検討メモ

## データ
組み込み向けの、軽量ライブラリとして提供するため以下を満たすこと。  

1. マルチインスタンスに対応するため制御データは構造体で一元管理とする。  
   インスタンスのメモリ領域は静的確保させる。内部staticデータ等も定義しない。  

2. 構造体は不透明型を採用し、CLIライブラリの制御データに対し外部からのアクセスはできないようにする。  
   APIを介する場合のみ、利用者は制御データの操作が可能となる。  

   また、公開する不透明型が確保するメモリ使用量は固定byteとする。  
   将来の拡張を考慮し、「64byte」とする。  

   ```h
   typedef struct
   {
       /* 不透明型を採用し、データ領域は64byteを確保する */
       uint8_t opaque[64]:
   } cli_handle_t;
   ```


3. CLIライブラリが使用するワークメモリは利用者が供給する。  
   コマンドライン用バッファ・実行コマンド(関数ポインタ)等の利用者によって必要とするメモリ使用量が異なるデータに関しては、利用者側に必要とするメモリ領域を保証してもらう。  

   コマンドライン用バッファは、利用者がメモリ領域の先頭ポインタと、メモリを使用する機能を通知する。  
   - メモリ領域の先頭ポインタ
   - メモリ領域のサイズ
   - コマンドラインの最大長
   - コマンドラインの履歴件数
   - 出力用バッファの最大長

   これらの設定から、メモリレイアウトと各機能に振り分けるメモリ開始位置のオフセットを算出しデータ構造内で管理する。  
   メモリを使用する機能は、メモリレイアウトとオフセットに応じて適切なメモリアクセスを行う。  

   実行コマンド(関数ポインタ)に関しても、利用者・アプリケーションが必要とするコマンド数が異なることを想定しており、固定長でコマンド用のメモリ領域を確保する必要はないと考える。そのため、コマンドの管理は連結リストを用いる。

   コマンドの先頭ポインタはCLIライブラリが保証し、先頭ポインタ以降の各ノードが必要とするメモリは、利用者側に保証してもらう。  


4. 利用者の環境に合わせた設定が必要なデータ用に専用のデータ構造を定義する、  
   例えば「3」で示したような、利用者がメモリ領域の確保であったり、任意の設定が必要なデータに関しては初期化用のデータ構造を定義し、設定が必要であることを明示する。  

   ```h
   typedef struct
   {
       /* ユーザーが個別に設定するデータを定義 */
       /* コールバック */
       /* ワークバッファ等... */
       int (*io_write_cb)(const char *p, uint32_t s);
   
       void *work;
       uint32_t work_mem_size;
   
       uint32_t max_line_length;
       uint32_t history_depth;
       uint32_t max_io_write_length;
   } cli_config_t;
   ```
