# CLIライブラリ 設計メモ
検討内容を記載する。  


## 機能
CLIライブラリは、テキストのコマンドを入力し、マイコンの操作を実現するソフトウェアモジュールである。  

テキストデータの管理・コマンドの実行を行う`コマンドモジュール`と、キャラクタ・テキストデータの出力を行う`アウトプットインターフェース`をCLIライブラリの機能として提供する。  
キャラクタデータの入出力や、テキストデータの描画は本ライブラリの責務とはしない。  

入出力・描画デバイスと、CLIライブラリの関連を示す図を以下に記載する。  

```text
キーボード等の入力デバイスから、キャラクタデータを入力
↓
=============================
入力モジュール(UART, BLE, CDC等...)
↓
CLIライブラリ
(テキストデータの作成・編集、コマンドハンドラー)
↓
出力モジュール(UART, BLE, CDC等...)
=============================
↓
コンソール等の表示器に現在のコマンドラインや処理結果を描画
```

---



### コマンドモジュール
**コマンドモジュール**は、テキストデータの管理・コマンド確定時のテキストデータ解析、コマンドのハンドラーを行う。  

コマンドモジュールには、1byte毎のキャラクタデータをプッシュ方式で入力する。  
入力したキャラクタデータからコマンドとなるテキストデータの作成・編集を行い、コマンド確定時にハンドラー機能を実行する。  

また、キャラクタデータの文字コードは、`ASCII`コードを想定している。  
そのほかの文字コード（UTF-8、Shaft_JIS等）については動作の保証はしない。  

---



#### エディター
入力されたキャラクタデータからテキストデータの作成・編集と、履歴操作等を行う。  
また、作成・編集中の現在のテキストデータをコマンドライン(入力行)と記載する。
確定・使用したテキストデータはライブラリ内のストレージに保存し、保存済みのテキストデータを履歴と記載する。  

作成するコマンドライン(入力行)の、フォーマットは、以下のいずれかである必要がある。  

- コマンドの1単語のみ
```shell
cmd
```

- コマンドと引数合わせた複数単語(コマンドと引数合わせて8単語まで対応)
```shell
# 引数は最大で7つまで対応
cmd arg1 arg2 ...
```

---



#### パーサー
コマンドラインの確定時に引数が存在する場合は、スペース区切りでパースされる。  
パース後のコマンドラインは、コマンドと引数を合わせたパラメータ数と、パース後のコマンドラインを指すポインタに分離される。
引数がない場合はコマンドのみをポインタは保持する。  

なお、パースされた後のコマンドラインはコマンド実行時に使用される。  
本データの生存サイクルは、コマンドライン確定→パース→コマンド実行までの期間となり、そのほかは保証しない。  

```c
int argc = 0;
char *argv[8];

argv[0] = "cmd";
argv[1] = "arg1";
argv[2] = "arg2";

argc = 3;
```

---



#### ハンドラー
CLIライブラリは、パースされたコマンドラインのコマンドに一致するコマンド処理のハンドラーを行う。  
コマンド処理は、ユーザーが定義し、CLIライブラリ、またはユーザーアプリケーションの初期化時に登録しておく必要がある。  

コマンド処理の実行後は、次回のコマンドラインを作成することが可能となる。  

---



### アウトプットインターフェース
**アウトプットインターフェース**は、キャラクタ・テキストデータの出力を行うインターフェースとして定義する。  

CLIライブラリは、外部への入出力機能は責務としていない。  
そのため、アウトプットインターフェースを使用する場合はCLIライブラリの初期化時に出力用モジュールのコールバック登録が必要になる。  

キャラクタ・テキストデータの出力時は、アウトプットインターフェースの呼び出しを契機に登録したコールバックへ責務を移譲する。  

```text
CLIライブラリのコマンドモジュール(またはユーザーアプリケーション)から、出力を要求
↓
アウトプットインターフェースの呼び出しを契機に、コールバックを起動
↓
出力モジュール(UART, BLE, CDC等...)
```

## データ
組み込み向けの、軽量ライブラリとして提供するため以下を満たすこと。  

1. マルチインスタンスに対応するため制御データは構造体で一元管理とする。  
   インスタンスのメモリ領域は静的確保させる。内部staticデータ等も定義しない。  

2. 構造体は不透明型を採用し、CLIライブラリの制御データに対し外部からのアクセスはできないようにする。  
   APIを介する場合のみ、利用者は制御データの操作が可能となる。  

   また、公開する不透明型が確保するメモリ使用量は固定byteとする。  
   将来の拡張を考慮し、「64byte」とする。  

   ```h
   typedef struct
   {
       /* 不透明型を採用し、データ領域は64byteを確保する */
       uint8_t opaque[64]:
   } cli_handle_t;
   ```


3. CLIライブラリが使用するワークメモリは利用者が供給する。  
   コマンドライン用バッファ・実行コマンド(関数ポインタ)等の利用者によって必要とするメモリ使用量が異なるデータに関しては、利用者側に必要とするメモリ領域を保証してもらう。  

   コマンドライン用バッファは、利用者がメモリ領域の先頭ポインタと、メモリを使用する機能を通知する。  
   - メモリ領域の先頭ポインタ
   - メモリ領域のサイズ
   - コマンドラインの最大長
   - コマンドラインの履歴件数
   - 出力用バッファの最大長

   これらの設定から、メモリレイアウトと各機能に振り分けるメモリ開始位置のオフセットを算出しデータ構造内で管理する。  
   メモリを使用する機能は、メモリレイアウトとオフセットに応じて適切なメモリアクセスを行う。  

   実行コマンド(関数ポインタ)に関しても、利用者・アプリケーションが必要とするコマンド数が異なることを想定しており、固定長でコマンド用のメモリ領域を確保する必要はないと考える。そのため、コマンドの管理は連結リストを用いる。

   コマンドの先頭ポインタはCLIライブラリが保証し、先頭ポインタ以降の各ノードが必要とするメモリは、利用者側に保証してもらう。  


4. 利用者の環境に合わせた設定が必要なデータ用に専用のデータ構造を定義する、  
   例えば「3」で示したような、利用者がメモリ領域の確保であったり、任意の設定が必要なデータに関しては初期化用のデータ構造を定義し、設定が必要であることを明示する。  

   ```h
   typedef struct
   {
       /* ユーザーが個別に設定するデータを定義 */
       /* コールバック */
       /* ワークバッファ等... */
       int (*io_write_cb)(const char *p, uint32_t s);
   
       void *work;
       uint32_t work_mem_size;
   
       uint32_t max_line_length;
       uint32_t history_depth;
       uint32_t max_io_write_length;
   } cli_config_t;
   ```
